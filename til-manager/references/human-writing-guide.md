# Human Writing Guide for TIL

> 원본: human-writing 스킬 (Write content that sounds natural, conversational, and authentically human)
> 적용 대상: 한국어 TIL 작성에 맞게 어댑트

TIL은 나를 위한 기록이다. 발표 자료도, 블로그 포스트도 아니다.
6개월 후의 내가 읽었을 때 "아 그때 그랬지" 하고 떠오르는 글이 좋은 TIL이다.

---

## Core Principle

**동료한테 커피 마시면서 설명하듯 써라. 발표 자료처럼 쓰지 마라.**

좋은 글은 구체적이고, 솔직하고, 대화하듯 읽힌다.
나쁜 글은 막연하고, 안전빵만 치고, 어디서나 볼 수 있는 보고서 문체다.

---

## ❌ 피해야 할 AI 패턴들

### 1. 과장된 표현 / 막연한 주장 (Vague Claims)

원본 원칙: "Every claim should be backed by evidence."

```
❌ "API 응답 속도를 유의미하게 개선하였다"
❌ "성능이 크게 향상되었다"
❌ "효과적으로 리팩토링을 수행하였다"

✅ "API 응답이 300ms에서 20ms로 줄었다"
✅ "캐시 붙이니까 확 빨라졌다 — 체감이 다름"
✅ "UserService에서 인증 로직을 AuthService로 뽑아냈다"
```

규칙: 숫자가 있으면 숫자를 쓴다. 없으면 체감을 쓴다. "유의미"같은 단어는 쓰지 않는다.

### 2. 기업 보고서 문체 (Corporate Buzzword Soup)

원본 원칙: "Empowering developers to leverage synergies..." → "Works with whatever you're already using."

```
❌ "체계적으로 접근하여 문제를 해결하였다"
❌ "최적화를 수행하여 효율성을 증대시켰다"
❌ "이를 통해 개발 생산성을 향상시킬 수 있었다"

✅ "하나씩 찾아보면서 해결했다"
✅ "최적화했다"
✅ "덕분에 좀 더 빨리 만들 수 있었다"
```

### 3. 불필요한 헤지(Hedging) / 수동태

원본 원칙: "This cuts migration time in half." — 자신 있게 말하라.

```
❌ "~할 수 있을 것으로 예상된다"
❌ "~에 도움이 될 수 있을 것이다"
❌ "성능 개선이 이루어졌다" (수동태)

✅ "이러면 반은 줄어든다"
✅ "이게 도움이 된다"
✅ "성능을 개선했다" (능동태)
```

### 4. 뻔한 전환어 (Generic Transitions)

원본 원칙: "Just start the next section. You don't need a transition."

```
❌ "이를 통해..."
❌ "이러한 경험을 바탕으로..."
❌ "또한, ~뿐만 아니라..."
❌ "말할 것도 없이..."

✅ 그냥 다음 문장을 시작한다
✅ "근데" / "그래서" / "그리고" 같은 구어체 접속사
✅ 필요하면: "이게 왜 중요하냐면:"
```

### 5. 로봇 리스트 (Robotic Lists)

원본 원칙: 리스트 항목에 구체적인 이유를 넣어라.

```
❌ "오늘 배운 점:
1. 코드 품질의 중요성
2. 테스트의 필요성
3. 문서화의 가치"

✅ "오늘 배운 것 3가지:
- SRP 지키니까 테스트 짜기가 훨씬 쉬워졌다
- refresh token race condition은 Redis SETNX로 해결 가능
- OAuth2 인가 코드 플로우에서 redirect URI 설정이 제일 까다롭다"
```

### 6. 경어체 / 과거 수동

```
❌ "~하였습니다" → ✅ "~했다"
❌ "~되었습니다" → ✅ "~됐다"
❌ "~에 대해 학습하였다" → ✅ "~를 배웠다"
❌ "~할 수 있었습니다" → ✅ "~할 수 있었다"
```

## ✅ 사용해야 할 사람 패턴들

### 1. 구체적 디테일 (Specific Details)

원본 원칙: "Many developers struggle" → "We've all copy-pasted from a migration guide, missed an edge case, and spent 2 hours debugging."

```
❌ "많은 개발자들이 캐시 무효화에 어려움을 겪는다"
✅ "캐시 무효화 안 하고 넣었다가 데이터 꼬여서 2시간 삽질했다"

❌ "성능이 개선되었다"
✅ "쿼리 시간이 847ms에서 12ms로 줄었다"

❌ "여러 프레임워크를 지원한다"
✅ "Spring Boot, CodeIgniter3에서 테스트했다"
```

### 2. 자신감 있는 직접 표현 (Direct, Confident Language)

```
❌ "이 방법이 도움이 될 수도 있다"
✅ "이 방법이 도움이 된다"

❌ "일부 경우에 유용할 수 있다"
✅ "파일이 10개 넘으면 이걸 쓰자"
```

### 3. 솔직한 한계 인정 (Honest Limitations)

원본 원칙: "This won't catch dynamic imports. You'll need to fix those manually."

```
❌ "완벽하게 해결할 수 있는 방법을 찾았다"
✅ "일단 TTL로 땜빵했는데 근본적인 해결은 아닌 것 같다"

❌ "모든 케이스를 커버한다"
✅ "edge case 5%는 수동으로 잡아야 한다. 그래도 30%보다는 낫다"
```

이건 TIL에서 특히 중요하다. "개선점" 섹션은 본질적으로 솔직한 한계 인정이다.

### 4. 대화체 곁들이기 (Conversational Asides)

원본 원칙: "You could write a 400-line script for this. We did. It broke on Unicode."

```
✅ "Redis lock 걸어보려고 했는데... SETNX 한줄이면 되는 걸 30분 삽질했다"
✅ "문서 다 읽었는데 결국 StackOverflow에서 답 찾음"
✅ "이론적으로는 완벽한데, 프로덕션에선 어떨지 모르겠다"
```

### 5. 능동태, 현재 시제 선호 (Active Voice)

```
❌ "패키지가 설치될 수 있다" (수동)
✅ "패키지를 설치한다: pip install redis" (능동)

❌ "변환 품질에 개선이 이루어졌다"
✅ "변환 품질을 78%에서 94%로 올렸다"
```

### 6. 입력 톤 미러링

사용자가 쓴 그대로의 느낌을 최대한 살린다. 이것이 TIL 스킬에서 가장 중요한 원칙이다.

| 사용자 입력 | AI 문체 (X) | 사람 문체 (O) |
|------------|------------|-------------|
| "캐시 붙이니까 확 빨라짐" | "캐시를 적용하여 응답 속도가 유의미하게 개선되었다" | "캐시 붙이니까 응답이 확 빨라졌다" |
| "삽질 좀 했음" | "문제 해결 과정에서 다소 시행착오를 겪었다" | "좀 삽질했다" |
| "ㅋㅋ Redis 날려먹을 뻔" | "Redis 데이터 유실 위기를 경험하였다" | "Redis 날려먹을 뻔했다 ㅋㅋ" |

## 문장 리듬 변화

모든 문장이 "~했다. ~했다. ~했다."로 끝나면 AI 느낌이 난다.

```
❌ Redis 캐시를 적용했다. API 응답 속도가 개선되었다. 하지만 캐시 무효화 전략이 부재했다.

✅ Redis 캐시를 붙였더니 응답이 확 빨라졌다. 
   근데 캐시 무효화를 안 생각하고 넣어서... 데이터 정합성 이슈가 한번 터졌다. 
   일단 TTL로 땜빵했는데, 근본적인 해결은 아닌 것 같다.
```

## 섹션별 톤 가이드

| 섹션 | 톤 | 예시 |
|------|-----|------|
| 잘한 점 - 상황 | 담담하게 팩트 | "OAuth2 로그인을 구현해야 했다" |
| 잘한 점 - 액션 | 구체적으로, 숫자로 | "Spring Security OAuth2 Client로 카카오 로그인 구현했다" |
| 잘한 점 - 칭찬 | 진심으로, 약간 뿌듯하게 | "처음인데 하루 만에 동작하게 만든 건 좀 잘한 듯" |
| 개선점 - 문제 | 솔직하게 | "무효화 전략 없이 캐시를 때려넣었다" |
| 개선점 - 원인 | 분석적이되 자책 없이 | "급하게 넣다 보니 그 부분을 못 챙겼다" |
| 개선점 - 액션플랜 | 구체적 다음 스텝 | "내일 Cache-Aside vs Write-Through 비교해보자" |
| 배운 점 - 배움 | 깨달음의 순간 | "아 이래서 SRP가 중요한 거구나" |
| 배운 점 - 의미 | 왜 기억할 만한지 | "캐시 넣기 전에 무효화부터 먼저 생각하자" |
| 핵심 내용 | **예외: 기술 문서 톤 OK** | "Cache-Aside: 읽기 시 캐시 miss → DB 조회 → 캐시 저장" |

> 핵심 내용 섹션만 유일하게 딱딱해도 괜찮다. 레퍼런스로 찾아볼 때는 간결·정확이 우선.

## 감정 표현 사전

AI가 잘 못 쓰는, 사람만 쓰는 자연스러운 표현들:

**긍정:** "뿌듯하다", "좀 잘한 듯", "다행이다", "해냈다!", "드디어 됐다", "이거 좀 괜찮은데?"

**부정/아쉬움:** "좀 아쉽다", "찝찝하다", "아직 갈 길이 멀다", "또 삽질했다", "멘붕"

**불확실:** "아직 잘 모르겠다", "좀 더 파봐야 할 듯", "일단 이렇게 했는데 맞는 건지..."

**깨달음:** "아 이래서 ~하는 거구나", "드디어 이해됐다", "그동안 왜 몰랐지", "이걸 진작 알았으면..."

## Self-Check 질문 (작성 후 검증)

원본 human-writing 스킬의 7가지 질문을 TIL에 맞게 어댑트:

1. **사람이 입으로 이렇게 말할까?** 아니면 다시 써라.
2. **모든 주장에 근거가 있나?** 숫자, 코드, 체감 중 하나는 있어야 한다. 없으면 빼거나 구체화.
3. **이 문장이 아무 TIL에나 들어가도 어색하지 않나?** 그렇다면 더 구체적으로.
4. **나를 바보 취급하는 느낌이 드나?** 그렇다면 독자(= 미래의 나)를 더 신뢰하라.
5. **확신이 없어서 헤지하고 있나?** 사실을 확인하거나, 불확실함을 솔직히 인정하라 ("아직 잘 모르겠다").
6. **이 전환어, 삭제해도 되나?** 된다면 삭제.
7. **정보 대신 감탄으로 시작하고 있나?** 그렇다면 정보부터 써라.

## Quick Fixes

### 너무 딱딱하면:
- "활용하다" → "쓰다"
- "~하기 위하여" → "~하려고"
- "현 시점에서" → "지금"
- "~의 목적으로" → "~하려고"
- "매우", "상당히", "실로" 같은 수식어 삭제

### 너무 막연하면:
- 구체적 숫자를 추가 (300ms → 20ms)
- 실제 기술명을 넣기 (Spring Security OAuth2 Client)
- 코드 예시를 포함
- 구체적 edge case 언급
- "유의미한" → 구체적 수치 또는 체감

### 너무 과장이면:
- 최상급("최적의", "완벽한") → 비교로 대체 ("이전보다 나은")
- "혁신적" → "이전과 다른 점은"
- 감탄부호 줄이기
- 첫 문장 잘라보기 (보통 마케팅 문구)
