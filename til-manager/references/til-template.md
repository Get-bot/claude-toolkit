## 작성 원칙

1. **헤딩은 핵심 키워드로** — 숫자 대신 항목의 내용을 요약하는 키워드를 헤딩에 쓴다 (예: `### OAuth2 인가 코드 플로우 구현`)
2. **라벨은 블록 헤더, 내용은 bullet로** — `**상황**` / `**액션**` / `**문제**` 같은 라벨은 볼드 한 줄로 두고, 그 아래에 `-` bullet으로 여러 포인트를 나열한다. 한 줄로 끝내지 말고 배경·디테일·판단 근거가 드러나게 여러 bullet으로 풀어 쓴다.
3. **빈 섹션은 억지로 채우지 않는다** — 해당 없으면 "오늘은 특별히 없음"으로 표기
4. **기술 용어는 영어 그대로** — Spring Boot, Redis, Kafka 등
5. **구체적으로 쓴다** — "잘했다" (X) → "A 기능의 API 응답시간을 300ms에서 20ms로 줄였다" (O)
6. **칭찬은 진정성 있게** — 사용자의 톤에 맞추되 과장하지 않는다
7. **액션플랜은 실행 가능하게** — "앞으로 잘하자" (X) → "매일 PR 올리기 전 테스트 커버리지 확인하자" (O)
8. **핵심 내용은 미래의 나를 위한 레퍼런스** — "배운 점"은 회고, "핵심 내용"은 기술 노트. 6개월 후에 검색해서 바로 쓸 수 있을 정도로 구체적으로 적는다.
9. **핵심 내용의 코드/참고자료는 선택** — 코드 없이 개념만 정리해도 OK. 억지로 코드를 넣지 않는다.

## 잘한 점

### 카카오 OAuth2 로그인 구현

**상황**
- 기존엔 이메일/비밀번호 로그인만 있었는데 신규 유입 전환율이 낮다는 피드백이 쌓임
- PM이 "소셜 로그인 없으면 가입 단계에서 절반은 이탈한다"고 해서 이번 스프린트에 카카오부터 붙이기로 함
- OAuth2는 처음이었음

**액션**
- Spring Security OAuth2 Client로 인가 코드 → 액세스 토큰 → 사용자 정보 조회 파이프라인 전체 구현
- 기존 `UserService`에 소셜 가입 분기를 넣으면 책임이 뒤섞일 것 같아 `SocialAuthService`로 분리
- provider별 전략 패턴으로 설계 → 나중에 구글/네이버 붙일 때 provider만 추가하면 되는 구조

**칭찬**
- 문서만 보고 덤볐는데 하루 만에 end-to-end로 동작하게 만든 것
- 급할 때 "일단 돌아가게" 짜는 습관을 의식적으로 피하고 처음부터 확장성 고려해서 전략 패턴으로 분리한 판단
- 문서랑 코드 왔다갔다하면서 끝까지 해낸 게 좀 뿌듯

## 개선점

### JWT refresh race condition

**문제**
- refresh 로직에서 간헐적으로 401이 터짐
- 재현이 잘 안 돼서 처음엔 네트워크 문제인 줄 알고 2시간 헤맴
- 로그 파보니 refresh 요청이 동시에 2~3개 들어올 때만 재현되는 패턴

**원인**
- refresh token을 1회용으로 쓰면서 사용 즉시 무효화하는 구조
- 여러 탭에서 동시에 401이 나면 refresh 요청이 병렬로 발생
- 첫 요청이 token을 무효화한 직후 두 번째 요청이 이미 유효하지 않은 token으로 시도
- 단일 탭 테스트만 해서 완전히 놓침

**액션플랜**
- 옵션 1: Redis SETNX로 refresh 요청 직렬화
- 옵션 2: grace period 둬서 이전 token 짧은 시간 유효화
- 내일 둘 다 POC 짜고 성능/복잡도 비교 후 결정
- 프론트 땜빵: refresh 요청을 Promise 레벨에서 dedupe (오늘 배포 완료)

## 배운 점

### SRP와 책임 분리의 체감

**배움**
- 인증 로직이 `UserService`에 섞여 있으니까 테스트 짜기가 너무 힘들었음
- `AuthService`로 분리하니까 mock 대상이 명확해지고 테스트 케이스도 훨씬 간단해짐
- 아 이래서 SRP가 중요한 거구나 하는 걸 실무에서 처음 체감

**의미**
- "일단 돌아가게" 만든 코드가 쌓이면 결국 리팩토링 비용이 눈덩이가 된다
- 처음부터 책임 분리를 의식하자 — 특히 인증/결제 같은 크로스커팅 관심사는 반드시 별도 서비스로
- 다음 기능 만들 때 "이거 어느 서비스에 속하지?"를 먼저 질문하는 습관 들이자

## 핵심 내용

### 키워드
- `OAuth2 Authorization Code Flow`, `Spring Security OAuth2 Client`, `JWT Refresh Token Rotation`

### 요약
- OAuth2 인가 코드 플로우: 사용자 인증 → 인가 코드 발급 → 액세스 토큰 교환 → 리소스 접근. Spring Security에서는 `OAuth2LoginAuthenticationFilter`가 이 과정을 처리한다.
- JWT refresh 시 동시 요청 문제는 token rotation + Redis lock으로 해결 가능. refresh token을 1회용으로 만들고, 동시 요청은 Redis SETNX로 직렬화.

### 코드/명령어
- ```yaml
  # application.yml - 카카오 OAuth2 설정
  spring.security.oauth2.client.registration.kakao:
    client-id: ${KAKAO_CLIENT_ID}
    authorization-grant-type: authorization_code
    redirect-uri: "{baseUrl}/login/oauth2/code/kakao"
    scope: profile_nickname, account_email
  ```

### 참고 자료
- Spring Security OAuth2 공식 문서: https://docs.spring.io/spring-security/reference/servlet/oauth2/login.html
- 카카오 로그인 REST API: https://developers.kakao.com/docs/latest/ko/kakaologin/rest-api

데이터 정합성 이슈가 한번 터졌음. TTL로 임시 처리했는데 근본적인 해결은 아닌 것 같음.

## 잘한 점

### Redis 캐시 적용으로 API 속도 개선

**상황**
- API 응답이 느려서 사용자 체감 속도 이슈가 계속 나오고 있었음
- 특히 상품 목록 조회가 병목이라 캐시 전략을 고민하기 시작

**액션**
- Redis 캐시를 붙여서 응답 속도를 대폭 개선 (상품 목록 기준 약 600ms → 80ms)
- `@Cacheable`로 읽기 경로에 캐시 적용, 기존 서비스 코드는 최소 변경

**칭찬**
- 성능 문제를 직접 캐치해서 캐시까지 적용한 것
- 지표로 개선 효과를 확인한 뒤 PR에 before/after 수치를 박아 넣은 점이 스스로 마음에 듦

---

## 개선점

### 캐시 무효화 전략 부재로 정합성 이슈

**문제**
- 캐시 무효화 전략을 안 세우고 적용해서 데이터 정합성 이슈가 한 번 터짐
- 관리자 페이지에서 상품 정보 수정했는데 사용자 화면에 반영이 안 돼서 CS 들어옴

**원인**
- 급하게 캐시를 넣다 보니 무효화 전략을 미리 안 짰음
- TTL(5분)로 일단 땜빵했는데 5분 동안 stale data 노출 구조
- 쓰기 경로에서 캐시 invalidate를 아예 빼먹음

**액션플랜**
- Cache-Aside vs Write-Through 비교 문서 정리
- 우리 서비스 읽기/쓰기 비율 보면 Cache-Aside가 적합 → 다음 스프린트에 `@CacheEvict` 도입
- 캐시를 건드리는 모든 PR 체크리스트에 "무효화 경로 확인" 항목 추가

---

## 배운 점

### Cache-Aside vs Write-Through 트레이드오프

**배움**
- Cache-Aside는 읽기 중심일 때, Write-Through는 쓰기 정합성이 중요할 때 쓴다
- 둘의 트레이드오프를 오늘 실무에서 직접 체감 (CS 들어온 순간 이해도가 확 올라감)

**의미**
- 캐시는 "붙이면 빨라지는 것"이 아니라 "무효화 전략까지 세트"라는 걸 몸으로 배움
- 앞으로 캐시 넣기 전에 무효화 경로부터 먼저 설계하자
- 성능 개선 작업은 지표뿐 아니라 정합성 영향도 같이 검토해야 안전

## 핵심 내용

### 키워드
- `Cache-Aside`, `Write-Through`, `TTL`, `@Cacheable`, `@CacheEvict`

### 요약
- **Cache-Aside**: 앱이 캐시를 직접 관리. 읽기: 캐시 miss → DB 조회 → 캐시 저장. 쓰기: DB 업데이트 → 캐시 삭제(invalidate). 읽기 중심 워크로드에 적합.
- **Write-Through**: 캐시를 통해 DB에 쓰기. 쓰기 시 캐시와 DB 동시 업데이트. 정합성이 중요한 경우 적합하지만 쓰기 지연 증가.
- TTL만으로 무효화하면 TTL 동안 stale data 노출 → 명시적 invalidation 필수.

### 코드/명령어
- ```java
  // Cache-Aside with Spring
  @Cacheable(value = "products", key = "#id")
  public Product getProduct(Long id) { ... }
  
  @CacheEvict(value = "products", key = "#id")
  public void updateProduct(Long id, ProductDto dto) { ... }
  ```
````
